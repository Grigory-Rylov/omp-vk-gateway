# VK → oh-my-pi Gateway

VK-бот, который передаёт сообщения из чата в агент `oh-my-pi` (`omp --mode rpc`)
и возвращает его ответы обратно в VK. На каждый чат заводится отдельный
агентский subprocess со своей рабочей директорией и своей историей диалога.

## Требования

- Go 1.27+
- установленный `omp` (по умолчанию ищется `~/.bun/bin/omp`; свой путь можно
  указать в `agent_cmd`)
- конфигурация oh-my-pi в `~/.omp/agent/` (`models.yml`, `config.yml` —
  провайдер/модель)
- токен бота VK

## Сборка

```sh
sh ./build.sh
```

Собирает `omp-agent` и `omp-agent-restarter` и впечатывает текущее время
(UTC) в бинарники через `-ldflags` (`pkg/buildinfo`). Версия вида
`v<Version> (build <дата время>)` показывается в стартовом логе и в
сообщении бота в чате при старте.

## Конфигурация

Штатный пример — `config.json` в корне репозитория. Штатный поиск
`omp-agent` (в порядке приоритета):

1. рабочий каталог, из которого запущен процесс;
2. каталог, где лежит бинарник;
3. `$HOME/.config/omp-vk-gateway/config.json`.

Поля:

| Поле | Обязательное | Описание |
|---|---|---|
| `token_vk` | да | токен бота VK |
| `peer_id` | нет | основной чат: если > 0, **все** ответы уходят туда (и туда же приветственное сообщение при старте); 0 — ответы отправляются тому, кто написал |
| `thinking_peer_id` | нет | чат, куда зеркалятся «мысли» агента (рассуждения, запуски инструментов); 0 — не зеркалировать |
| `workdir` | нет | рабочая директория агентов по умолчанию; пустое значение — CWD шлюза. Приложения из VK скачиваются в `<workdir>/attachments` |
| `model` | нет | флаг запуска `--model provider/model`; пусто — модель из конфигурации omp |
| `thinking_level` | нет | флаг `--thinking` (`off`, `low`, `medium`, `high`, ...) |
| `approval_mode` | нет | флаг `--approval-mode` |
| `debug` | нет | `true` — DEBUG-уровень в `log_file` (каталог файла создаётся автоматически) |
| `log_file` | нет | файл логов; по умолчанию `debug/gateway.log` |
| `agent_cmd` | нет | команда запуска агента; если указан один путь, автоматически добавляется `--mode rpc`; по умолчанию `~/.bun/bin/omp` |
| `extra_args` | нет | дополнительные аргументы запуска агента |

Минимальный рабочий конфиг:

```json
{
  "token_vk": "5xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "peer_id": 123456789,
  "thinking_peer_id": 123456789,
  "workdir": "/home/user/project"
}
```

## Быстрый запуск

```sh
./omp-agent        # от имени пользователя с ~/.omp/agent и ~/.bun/bin/omp
./omp-agent -d     # с включённым DEBUG
```

При старте бот шлёт в `peer_id` сообщение с клавиатурой команд и со своей
версией (время сборки из `build.sh`), далее работает в long-poll: обычное
сообщение → ответ агента, команды — см. ниже.
Остановка — `Ctrl-C` / SIGTERM (все агентские процессы останавливаются вежливо).

## Долгий прогон: restarter

`omp-agent-restarter` следит за `omp-agent`:

- при падении шлюза перезапускает его (если падение было < 30 с после
  последнего запуска, делает паузу 5 с — защита от цикла аварий);
- потребляет файловые сигналы, которые шлюз пишет в свой CWD:
  - `.agent-restart` (команда `/restart` в чате) → стоп + старт шлюза;
  - `.agent-update` (команда `/update` в чате) → стоп, `git pull`,
    `sh ./build.sh` (или команда из `update_cmd`), старт. Требует
    git-checkout репозитория.

Запускать от каталога, где лежат `config.json` и бинарник `omp-agent`:

```sh
./omp-agent-restarter
```

Restarter опционально читает `config.json` из своего CWD (поля `debug`,
`workdir`, `gateway_cmd`, `update_cmd`). Без файла по умолчанию: бинарник
`./omp-agent` рядом с restarter'ом, работа в CWD.

## Команды в чате

| Команда | Действие |
|---|---|
| `/help` | список команд |
| `/clear` | очистить историю диалога (рабочая директория сохраняется) |
| `/newsession [path]` (`/n`) | сбросить сессию и при желании сменить рабочую директорию |
| `/status` | статус агента: модель, сессия, контекст, скорость, GPU (если есть nvidia-smi) |
| `/log` (`/logs`) | отправить файлы из папки `debug/` в чат |
| `/m` (`/models`) | список доступных моделей |
| `/r [provider/model]` | переключить текущую модель (без аргумента — список с клавиатурой) |
| `/abort` | остановить текущий ответ |
| `/restart` | перезапустить шлюз (нужен restarter; без него — стоп агентских процессов + файл сигнала) |
| `/update` | `git pull` + пересборка + перезапуск (нужен restarter) |

Обычный текст передаётся агенту; если агент уже отвечает, текст доносится в
текущий ход (steer).

## Логи

- файл из `log_file` (по умолчанию `debug/gateway.log`) — INFO/WARN всегда,
  DEBUG — при `debug: true` (или `-d`); каталог файла создаётся при старте;
- команда `/log` в чате — бот присылает содержимое `debug/`.

## Как работает

- на каждый чат — один subprocess `omp --mode rpc --cwd <workdir>`,
  JSONL-протокол по stdio, версия 2 (большие кадры собираются из
  `rpc_chunk`-кусков);
- финальный ответ — последнее сообщение ассистента, шлётся целиком одним
  сообщением; рассуждения (reasoning) накапливаются в течение сообщения и
  уходят в `thinking_peer_id` одним сообщением на завершённое сообщение
  ассистента (потоковая отправка по каждому токену упирается в
  флуд-контроль VK); запуски инструментов зеркалятся отдельными строками;
- ограничение VK 2000 символов: длинные ответы разбиваются на части с
  нумерацией `[i/n]`;
- если long-poll упал с `long poll failed` — сервер поллинга запрашивается
  заново; агентские процессы, упавшие по своей инициативе, перезапускаются.

## Если что-то не работает

- `config.json not found` — положите конфиг в CWD запуска, рядом с бинарником
  или в `$HOME/.config/omp-vk-gateway/`;
- `config.json must set token_vk` — токен не заполнен;
- агентский процесс не стартует (ответ «агент-процесс недоступен») — проверьте
  путь в `agent_cmd`, наличие `~/.omp/agent/` и лог `debug/gateway.log`;
- `/update` не срабатывает — restarter должен работать и быть запущен из
  каталога с git-checkout'ом.
